    Boxbox 0.7.0: cheaper models for routine work, a brief for every task, and exact cost per model

    You asked for a release that cuts cost without cutting quality. Cheaper Claude models (Sonnet, Haiku) build, search, run checks and fill pages, each from a precise task brief. The strong session model (Opus) keeps planning, decisions and review. A hook enforces the routing, and the pit wall shows exactly which model did what and what it cost. It is done when all of that is built, tested and shipped as 0.7.0, with Codex unchanged apart from gaining task briefs.

    read before the decisions

    What this project is, and who it serves

    Boxbox is a plugin for AI coding agents (Claude Code, Codex, Cursor and others). It makes the agent work the way a careful engineer would: read the code, plan the work as milestones, epics and tasks, ask the developer for the decisions that matter, build one tested unit at a time, and stop for review with a page that teaches what was built. The plugin is mostly Markdown "skills", which are instructions the agent loads by name, in skills/. Two small programs sit beside them. One is a set of hooks in hooks/, commands Claude Code runs on every event. The other is a local web page called the pit wall, served by skills/boxbox-setup/kit/pitwall/server.js, which shows the developer live what the agent is doing and what it costs. It serves developers who want an agent to do the typing while they stay in control and keep understanding their code.

    Stack
    Node.js 18+ with no npm dependencies (skills/boxbox-setup/kit/pitwall/server.js, hooks/boxbox-event.js), bash (hooks/boxbox-event, hooks/session-start), Markdown skills (skills/*/SKILL.md), static HTML/CSS/JS pages (skills/boxbox-setup/kit/templates/), Python 3 for the template generator (tools/gen-templates.py)
    How it runs
    Tests: node --test tests/pitwall/*.test.js. Plugin check: claude plugin validate .. Pit wall: node .boxbox/pitwall/server.js --ensure. No build step and no linter.
    Entry points
    The boxbox skill (skills/boxbox/SKILL.md); the hooks registered in hooks/hooks.json (Claude Code) and hooks/hooks-codex.json (Codex); the pit wall at http://127.0.0.1:4747/

    How it is built

    Claude Code runs the agent and fires hook events. The bash hook hooks/boxbox-event catches every event, applies the pause gate, and passes the event to hooks/boxbox-event.js. That file writes a line for most events to .boxbox/live/events.jsonl (it skips its own say commands and most notifications), and registers each transcript in sessions.jsonl. The pit wall server reads those files plus Claude Code's own transcripts (the JSONL log of every message, with token usage) and pushes the state to the page in the browser. The skills write files in .boxbox/, run the tiny say script to announce their stage (it writes stage.json, waiting.json and an event line), and run three pit wall commands: server.js --ensure, server.js --summary and check-page.js. In 0.7, four new pieces join this picture: agent files in agents/, a routing gate inside the hook, per-model accounting in the server, and a status line script.

    How a request travels today

    The path that 0.7 changes is a subagent's life, from the main agent calling the Agent tool to its tokens showing on the pit wall. Here it is in 0.6, step by step. The gaps 0.7 fills are named at each step.

    1. The main agent calls the Agent toolhooks/hooks.json:35

      Claude Code fires PreToolUse with tool_name: "Agent" and the call's subagent_type, prompt and, if passed, model. Every PreToolUse goes to the bash hook (matcher *).

    2. The bash hook decides sync or backgroundhooks/boxbox-event:50

      Only SessionStart and pit wall commands run node synchronously, so they can answer Claude Code. Everything else, Agent calls included, reaches node only in the background, so node cannot allow or deny them. (The bash pause gate before it can still deny any call.) The routing gate needs a synchronous node path for Agent and Task calls.

    3. The call is logged as crew workhooks/boxbox-event.js:105

      classify maps Agent, Task and Codex's spawn_agent to the kind crew. It ignores the model field.

    4. The subagent starts and stopshooks/boxbox-event.js:406

      Both events append a crew line. Only SubagentStop registers the subagent's transcript in sessions.jsonl, under the parent's session id, so a running subagent's tokens are not counted until it ends.

    5. The server reads every transcriptskills/boxbox-setup/kit/pitwall/server.js:378

      refreshSessions tails each registered transcript. ingestClaudeLines keeps one entry per message, with its model and a sub tag for subagents.

    6. Tokens are grouped by unit and sessionskills/boxbox-setup/kit/pitwall/server.js:198

      aggregate buckets each entry by the stage active at its timestamp: epic, task, session. It never groups by model or by subagent, so a subagent's tokens fold into the parent's session row.

    7. The page shows itskills/boxbox-setup/kit/pitwall/index.html:564

      renderTiming draws a sessions table, which has a Model column but no cost per model, and a per-task table. renderLanes (line 511) draws three lanes: Driver, Pit crew and Steward.

    Patterns and conventions to follow

    • No dependencies: the server and hook use Node built-ins only (skills/boxbox-setup/kit/pitwall/server.js:11). New code, the status line included, stays dependency-free, so a fresh clone runs with nothing to install.
    • Pure parts are exported and tested: server.js keeps a "pure parts (tested)" block (skills/boxbox-setup/kit/pitwall/server.js:26) and exports it (skills/boxbox-setup/kit/pitwall/server.js:661). The hook exports its helpers the same way (hooks/boxbox-event.js:421). Routing rules, per-model aggregation and brief parsing should be pure functions exported for tests.
    • Tests use node:test and temp repos: tests/pitwall/gate.test.js:13 builds a throwaway repo with mkdtemp and runs the real bash hook against it. New gate tests follow this, so they exercise the bash and node paths together.
    • The hook fails open, except the pause gate: with no .boxbox/ it exits 0 within 50 ms (tests/pitwall/gate.test.js:23), while pause denies on any error (hooks/boxbox-event:24). The routing gate must decide which way it fails. That is a decision for you.
    • Never log content: events hold no file contents, prompt text or command output (skills/boxbox-setup/kit/GUIDE.md:126). Brief text and subagent prompts stay out of events.jsonl.

    Constraints

    • Claude Code only: agents, the gate, skill model: and the status line were verified as Claude Code features (see docs/routing-spike.md). Your spec requires Codex to behave as in 0.6, plus task briefs, with no errors from these parts.
    • Plugins cannot ship the main status line: only agent and subagentStatusLine take effect from a plugin's settings (spike 9). Setup must ask before writing the project's .claude/settings.json.
    • Worktrees start from the remote's default branch when a remote exists: parallel builders would miss the epic's earlier commits unless worktree.baseRef is "head". Without a remote they start from the current HEAD (spike 7).
    • Hook latency: every tool call passes through the hook (hooks/hooks.json:37), so the gate should add nothing to non-Agent calls. For the status line, Claude Code documents no timeout but cancels a running script when the next update comes (spike 9), so Boxbox sets itself a 50 ms target.
    • Budget: up to $30 of real Claude Code sessions for verification, but live demo runs are deferred for now.

    Subagents, in two paragraphs

    A subagent is a second Claude that the main agent starts with the Agent tool. It works in its own context window, starting from the prompt it is given rather than the conversation (Claude Code docs: subagents), and it can run on a different model. A plugin defines one in agents/<name>.md, with a model: line such as sonnet. Step 0 confirmed that this is honoured, and that a model passed on the call wins over the file (docs/routing-spike.md, sections 1 and 2).

    A hook is a command Claude Code runs on an event, with the event as JSON on its input. On PreToolUse a hook can answer "deny" with a reason. The agent reads the reason and tries again, and Step 0 saw it retry with the right agent (section 6). That is the whole enforcement mechanism of 0.7.

    Caching and worktrees, in one paragraph each

    Claude's API stores a prompt's beginning for a while. When the next call starts with exactly the same text, those tokens are billed as a cache read, much cheaper than fresh input. In Step 0 the second Haiku subagent read 4,460 tokens from the cache that the first one had written (docs/routing-spike.md, other observations). This is why every subagent prompt must start with the same fixed part.

    A worktree is a second folder checked out on another branch of the same repository, so two builders can edit files at once without stepping on each other. Step 0 found that Claude Code's worktree subagents start from the remote's default branch when the repo has a remote, unless worktree.baseRef says otherwise (section 7).

    How this can fail

    • highThe gate wrongly denies a call and blocks real work

      A rule bug or an agent type it does not know would stall the session. Limit: the gate judges only boxbox:* agents, its rules are pure functions with table tests, and models: auto switches it off.

    • highParallel builders start from main, not from the epic

      Their changes would merge against missing code. Limit: parallel mode refuses to start unless worktree.baseRef is "head", and stays off by default.

    • mediumSubagent tokens counted twice, or missed while running

      The cost would be wrong. Limit: register the transcript at start (its path can be derived), keep one entry per message id, and test against the real spike transcripts. Step 0 found no subagent lines in the main transcript.

    • mediumParallel subagents land on the wrong task

      The pit wall tracks one current unit, so two builders at once would share it. Limit: tie each subagent to its task through the Agent call, which agent-<id>.meta.json links back by toolUseId.

    • mediumA future Claude Code changes the resolution order

      It changed in v2.1.251 already. Limit: one function holds the order, FORCE is read from the environment and turns the gate off, and models: auto steps aside.

    • mediumEscalation loops or pushes through

      Limit: at most one escalation per task, logged as escalated. A failure on the session model stops and asks you.

    • lowThe status line slows the prompt

      Limit: it reads small local files only, with a timing test under 50 ms, and prints nothing on any error.

    • lowCache reads drop because the fixed prompt part changes

      Limit: build the fixed part only from files that stay put during a feature, and show the cache-read share per model so a drop is visible.

    • lowCodex errors on Claude-Code-only parts

      Limit: the gate acts only on Claude Code's Agent and Task calls, Codex payloads carry turn_id and are skipped, and the Codex fixture is tested.

    Words used on this page

    Session model
    The model the main conversation runs on, Opus in this project's sessions. Subagents set to inherit use it.
    Routing
    Choosing which model does which piece of work.
    Gate
    The new check in the PreToolUse hook that denies a subagent call breaking the routing rules.
    Brief
    A short file per task, .boxbox/<feature>/<epic>/tasks/<id>.md (the path your spec gives), holding everything a builder needs and nothing else.
    Escalation
    Retrying a task on the session model after a cheaper model failed or drifted.
    FORCE override
    CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1, which makes every subagent use CLAUDE_CODE_SUBAGENT_MODEL whatever the call or file says.
    Lane
    One row of the pit wall's Telemetry view, showing one worker's activity.
