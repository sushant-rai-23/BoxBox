    Decisions for Boxbox 0.7.0 model routing

    All five decisions are answered. One went against the recommendation: D5, shipping 0.7.0 on tests alone. Below them are the eleven small defaults I picked; any of them can still be changed.

    D1How should Boxbox tell Claude Code which model a subagent uses?

    answered

    An agent file in a plugin has one fixed model: line, but your spec has four modes (best, balanced, save, auto) plus per-task risk, per-epic overrides and escalation. One agent file cannot express all of that. Step 0 confirmed that a model passed on the Agent call wins over the agent file (see Subagents and model routing). Whatever is chosen here sets what the gate checks and how every build skill calls a builder.

    OptionWhat it means hereGainsCosts
    Always pass modelAgent files carry the balanced models as a fallback. In every mode except auto, the skills compute the model and pass it on each call, and the gate checks that the passed model equals the expected one.One rule, one place. The gate's job is a plain comparison. Modes, risk and escalation all work the same way, and the pit wall shows the requested model before the subagent even runs.Every call carries one more field. A main agent that forgets it gets denied once and retries.
    Agent files only, pass model for exceptionsThe agent files decide normally. model is passed only for risky tasks, epic overrides and escalation.Fewer fields on ordinary calls.best and save change the model of every agent, so they would need different agent files, which a plugin cannot switch per repo. The gate must also resolve "no model passed" the way Claude Code does, and that order already changed once (v2.1.251).
    Agent files set to inherit, always passLike the first option, but the files fall back to the session model.A forgotten field costs quality rather than money.Under auto, every agent would silently run on Opus, which defeats the point of auto.

    Recommendation: always pass model. It is the only option where all four modes work from one plugin, and it keeps the gate independent of Claude Code's resolution order (Step 0, section 2 of docs/routing-spike.md).

    Cost to change later
    Costly: the gate, the build skill and the agent files are all written around it.

    D2How should template-filling work run cheaper: skill model: lines, or the writer subagent?

    answered

    Part 4 of your spec asks for model: sonnet in some skills' frontmatter, "only in balanced and save". Step 0 found two limits. A skill's frontmatter is fixed text in the plugin, so it cannot change with a repo's mode, and best would still get Sonnet. The override also covers the whole turn, not one part of a skill. The spec's own fallback is to hand page-filling to boxbox-writer.

    OptionWhat it means hereGainsCosts
    Writer subagent onlyNo skill gets a model: line. The report's page-filling, the lessons pages and the setup refresh steps go to boxbox-writer, which takes its model from the mode like every other agent (D1).All four modes are honoured. One mechanism for everything. The pit wall counts the writer exactly, as a subagent.The writer must be handed its facts explicitly, so the prompt to it is longer than a skill turn.
    Skill model: sonnet as the spec saysSplit boxbox-report's page filling into a new small skill with model: sonnet, and add the same line to boxbox-lessons.No hand-off. It uses a native Claude Code feature.best mode is broken for these skills: they always run on Sonnet. Codex ignores the line, which is harmless.
    BothSkill lines for boxbox-lessons, the writer for pages.The cheapest turns.Two mechanisms to explain, and best is still broken for lessons.

    Recommendation: writer subagent only. Your spec says "only in balanced and save", and only a subagent can follow the mode (Step 0, section 4).

    Cost to change later
    Easy to add skill lines later. Removing a skill split later is costlier.

    D3Parallel mode: how should worktree builders start from the epic branch?

    answered

    Step 0 found that a subagent with isolation: worktree branches from the remote's default branch (main), not from the epic branch the session is on. A parallel builder would not see the epic's earlier tasks, and its merge back would be wrong. Read Git worktrees and merging first. Parallel mode stays off by default either way.

    OptionWhat it means hereGainsCosts
    Require worktree.baseRef: "head"When the developer turns parallel: on, setup asks to add "worktree": {"baseRef": "head"} to the project's .claude/settings.json. Parallel mode refuses to start without it and says why.Uses the documented setting. Step 0 showed it works. Nothing clever happens inside the builder.It changes a project settings file, which also affects the developer's own --worktree sessions in this repo.
    Builder rebases itselfNo settings change. The builder's first step in its worktree is git reset --hard <epic commit>, with the commit given in its brief.Works with any settings.Destructive git commands inside an agent. A builder that skips the step builds on the wrong base silently.
    Leave parallel mode out of 0.7Ship everything else and plan parallel mode for 0.8.A smaller, safer release.One of your spec's seven parts is missing.

    Recommendation: require worktree.baseRef: "head". It is the documented fix, it can be checked before starting, and it fails loudly rather than silently (Step 0, section 7).

    Cost to change later
    Easy: it is contained in the parallel epic, which is built last.

    D4When the routing gate itself breaks, should it allow the call or deny it?

    answered

    The gate runs on every Agent call. It can hit an error: plan.md cannot be parsed, node crashes, or a task id is missing. The pause gate in 0.6 fails closed: any error denies, because pausing is about your control (hooks/boxbox-event:24). The routing gate is about cost, not control.

    OptionWhat it means hereGainsCosts
    Fail open, and say soOn an internal error the call is allowed, and a gate-error event shows on the pit wall with the reason.A Boxbox bug never blocks your work. The worst case is one call on the wrong model, which you can see.A persistent bug silently stops enforcing until you notice the pit wall notice.
    Fail closedAny error denies with the error as the reason.Routing is never skipped.A plan.md typo stops every subagent call until it is fixed.

    Recommendation: fail open, and say so. The routing gate protects money, not safety or your control, and the context lists "the gate wrongly blocks real work" as the highest risk.

    Cost to change later
    Easy: one branch in the gate.
    Decided by
    Sushant Rai, 2026-10-14

    D5With demo runs deferred, what should "done" mean for 0.7.0?

    answered

    You said "no demo for now". Six of the spec's "done means" items need real Claude Code sessions: a balanced-mode run, a live gate denial, a forced double failure, a hand count of real transcripts, a parallel run with a forced conflict, and the status line in a live session. Unit tests can cover the logic of each, using fixtures copied from the real Step 0 transcripts. The release version and the README claims depend on what was actually verified.

    OptionWhat it means hereGainsCosts
    Build and test now, live checks before taggingAll epics are built with unit tests and real-transcript fixtures. The live checks become the last epic, run on a scratch repo when you say so. The version moves to 0.7.0 only after that.Nothing is claimed that was not seen. The live epic can wait as long as you like.The release is not taggable until the live epic runs.
    Ship 0.7.0 on tests aloneVersion 0.7.0 when the tests pass. The README marks the live-only items "not yet verified in a live session".Ships sooner.Users meet any live-only bug first.

    Recommendation: build and test now, with live checks before tagging. It keeps the guide's rule "never claim what you did not check", at no cost until you choose to run them.

    Override: ship 0.7.0 when the tests pass. The README marks the live-only items "not yet verified in a live session". No reason was given beyond "no demo for now".

    Cost to change later
    Easy: it only moves when the version bump and README claims happen.
