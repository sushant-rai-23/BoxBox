    What now exists, and how to see it working

    A subagent is a second Claude conversation that the main conversation starts for one job. It sees only the prompt it is given, does the job, and returns a short answer. Each subagent can run on a different model (a family such as opus, sonnet or haiku; opus is the strongest and dearest, haiku the cheapest). Model routing means choosing that family per job so cheap work does not burn expensive tokens. Before E1, Boxbox left this to Claude Code. Now four agent files fix the models (builder sonnet, scout haiku, runner haiku, writer sonnet) and hooks/routing.js answers "which model for this call?".

    The answer depends on models: in config.md: best (everything on the session model), balanced, save, or auto. A missing line means auto, which makes Boxbox pass no model and use no Boxbox agent, so repos set up before 0.7 behave exactly as before.

    The routing function returns the session model for a risky task under balanced. Run it:

    A headless Claude Code 2.1.296 session, started with --plugin-dir pointing at this repo and run in a scratch repo, showed the agents load and run on the routed model. boxbox:boxbox-scout called with model haiku ran on claude-haiku-5-5 and used only Glob and Grep. boxbox:boxbox-runner called with no model fell back to the model in its own file and also ran on claude-haiku-5-5. That session cost $0.244.

    The request path

    A "request" here is the main agent preparing one subagent call during a build. Each step below hands its result to the next.

    1. config.md holds the modeskills/boxbox-setup/kit/GUIDE.md:268

      The developer sets models: best | balanced | save | auto and parallel: off | on. Setup asks for it; a missing line is read as auto.

    2. parseModels reads the modehooks/routing.js:17

      Returns { mode, parallel, warning }. An unknown value becomes balanced plus a warning, which the session-start hook shows (hooks/boxbox-event.js:336).

    3. The plan carries size, risk and an epic modelhooks/routing.js:33

      parsePlanTasks reads | size: S | risk: no from each task line and a model: line from each epic. A missing size is M, a missing risk is no, and a value that is not a Claude family is ignored.

    4. expectedModel applies the ruleshooks/routing.js:62

      First match wins: auto, escalated, epic override, risk or L, then the table. It returns the family to pass, or null for no model.

    5. The build skill makes the Agent callskills/boxbox-build/SKILL.md:35

      The main agent follows this text: call boxbox:boxbox-builder with the family as model and the task id at the start of the description. The code does not make the call; a prompt tells the agent to.

    6. The agent file fixes the fallback and the toolsagents/boxbox-builder.md:4

      If the caller passes no model, the file's model: sonnet runs. The tools line limits what the agent can do.

    7. A failed task escalates through sayskills/boxbox-setup/kit/pitwall/say:52

      After two failures, or a diff three times too big, the main agent runs say escalated with the task id, then retries once on the session model. escalatedTasks (hooks/routing.js:55) turns those events into rule 2 on the next call. If the retry fails, the build stops.

    File by file

    Three ideas first. A plugin is a folder Claude Code loads to add skills (prompt files the agent reads), hooks (scripts Claude Code runs on events such as session start) and agents (subagent definitions). A hook here is a Node script that receives each event as JSON. Escalation means retrying a failed task on the stronger session model once, and recording that with say, a small bash script that appends a line to events.jsonl for the pit wall.

    The mode table

    The table is data, not branching code, so adding a mode is adding a row.

    Reading the mode

    The failure choice is deliberate: an unknown word is treated as balanced with a warning, and a missing line as auto. Missing means "this repo predates the feature", so it must not change behaviour.

    The rule

    This is the whole decision. It is a pure function: the same input gives the same output and it touches no file, which is why nine small tests can pin it down.

    The agent file

    An agent file is a Markdown file with a header (frontmatter) between two --- lines, then the prompt. The header is what Claude Code reads for the name, the fallback model and the tool list.

    The build skill instruction

    A skill is prose the agent follows. The routing rule only has effect because this line tells the main agent to use it.

    say escalated

    The script is bash. The line case "$text" in ""|--*) exit 0 ;; esac is a shell pattern match; exit 0 means quit quietly with success.

    Decisions made while building

    • A12: an agent test in tests/pitwall/agents.test.js, over no test: the four files are the contract, so a wrong model fails a test.
    • A13: setup refresh copies go to boxbox-runner, not the writer: copying files is mechanical, and the runner is cheaper.
    • A14: boxbox-lessons stays on the session model: it judges what to remember, which is not mechanical.
    • A15 (replaces A1): every description starts with the unit served, a task id, an epic id or setup, so the pit wall can attribute tokens to a unit.
    • A16 (replaces A3's form): say escalated "<reason>" --unit <id>, and with no unit nothing is written, because escalations are counted per task.
    • A17 (replaces an earlier idea that auto meant "Claude Code decides"): auto or no line means no Boxbox agents, no model and no escalation. With no model passed, a Boxbox agent runs on the model in its own file (observed in the spike), so auto would have meant a fixed model after all.

    Risks and edge cases not covered

    A separate agent on the session model reviewed the unit and found 2 must-fix and 6 should-fix problems. All were fixed in 600ac87, 3efb026 and 3bcd3d1; c81df65 was found while verifying. These were left alone on purpose.

    • mediumNo enforcement

      Nothing stops a main agent passing the wrong model. E3 adds the gate. Until then the rule is followed only because the prompt says so.

    • mediumA risky task under a Haiku session goes to haiku

      Rule 4 returns "session", and under a haiku session that is below the sonnet a normal task gets. The spec says "session model", so it was kept as written.

    • mediumAn unknown epic model: value is silently ignored

      familyOf returns null for it (hooks/routing.js:40), so the epic falls back to the table with no warning.

    • lowparallel: yes means off

      Only the exact word on turns it on (hooks/routing.js:27), and no warning is shown.

    • lowEscalations show as a generic run row on the pit wall

      The pit wall has no escalation display until E5. The event is recorded.

    • lowThe builder prompt describes a full brief that exists only from E2

      Until E2 the main agent writes a shorter brief by hand.

    • lowOne test leaves a temp directory behind

      It creates a folder under the system temp directory and does not remove it; the operating system clears it.

    • lowOld Claude Code versions reject claude plugin validate agents

      Claude Code 2.1.296, the version the VS Code extension runs, prints "Validation passed" for agents, for .claude-plugin/plugin.json and for .. The Homebrew claude on this machine is 2.1.100 and fails on agents with "No manifest found in directory". Run claude --version before trusting a validate result.

    • lowA live Boxbox build has not been run

      No real build followed the new build skill, and no live escalation or setup question has run (deferred as D5). Whether the prose reliably leads a fresh agent to route correctly is unknown; the reviewer read it but nobody ran it.

    Check yourself

    1. Why does models: auto mean no Boxbox agents at all, rather than "let Claude Code choose"?
      With no model passed, a Boxbox agent runs on the model in its own file, so a builder would quietly run on sonnet. Under auto the build skill uses plain subagents (skills/boxbox-build/SKILL.md:35) and expectedModel returns null at hooks/routing.js:64.
    2. What happens if the builder fails a task on the session model after an escalation?
      Nothing is retried. The skill says to update state.md, tell the developer what was tried, and wait. A task is escalated at most once, and a builder already on the session model has nothing to escalate to.
    3. Why does say escalated exit quietly when --unit is missing?
      The gate counts escalations per task, so an event with no unit cannot be used. Exiting 0 keeps say from ever failing a build (skills/boxbox-setup/kit/pitwall/say:54-55).
