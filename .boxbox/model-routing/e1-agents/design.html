    Design for E1: Routing config and fixed-model agents

    Four small agent files, each pinned to one model, and one pure function that says which model a call should use. The choice that matters most: a repo with no models: line means "pass no model", so existing 0.6 repos behave exactly as before.

    approved 2026-10-14no code written yet

    The problem

    Boxbox 0.7.0 wants cheap, mechanical work (searching, running checks, filling pages) to run on a smaller model, and the risky work to stay on the model you chose for the session. Today every call runs on the session model, so a search costs as much as a design review. E1 has to give the later epics two things: a place to say which models to use, and agents that cannot drift from the model they were written for.

    The plan states E1's outcome as: builds go through boxbox-builder, searches through boxbox-scout, checks through boxbox-runner, page filling through boxbox-writer, each on the model that the repo's models: mode and the task's size and risk call for. See the E1 section of .boxbox/model-routing/plan.md.

    The routing spike confirmed that this is possible. A plugin agent with model: sonnet ran on claude-sonnet-5-5 inside an Opus session, and a call that passed model: "haiku" to that same agent ran on claude-haiku-5-5, so the call beats the agent file (docs/routing-spike.md, sections 1 and 2). Plugin agents load as plugin:name, which is why ours are called boxbox:boxbox-builder and so on.

    The same spike gives the order Claude Code uses to pick a model: the environment override CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1 first, then the call's model, then the agent file's model:, then the session model. A plain CLAUDE_CODE_SUBAGENT_MODEL is only a default and changes nothing for agents that name a model (docs/routing-spike.md, section 3). That is why the design passes model on every call and keeps the agent file's model as a fallback only.

    The current code knows nothing about this. parseConfig at hooks/boxbox-event.js:236 returns only testCommand and pitwall, and the say script at skills/boxbox-setup/kit/pitwall/say:37 handles only the verbs stage and ask. The repo has no agents/ folder yet.

    New ideas in this design

    An agent fileA markdown file in the plugin's agents folder. Its top block names the agent, says what it is for, which model it uses and which tools it may touch. The text below is its standing instructions. is how Claude Code defines a subagent: a helper that the main session hands one job and that returns a short answer. Ours restrict the tools on purpose. The scout cannot edit anything because it has no edit tool.

    A family aliasA short model name such as opus, sonnet, haiku or fable that stands for the newest model of that family, instead of a full id like claude-sonnet-5-5. is the short name the Agent tool accepts for model. The routing function returns sonnet, not a full id, because ids change with every release and the alias keeps working.

    The session modelThe model the developer's own Claude Code session is running on, for example opus. It is the strongest model in the room and the one that decides, plans and reviews. is the model your chat runs on. "First match wins" means the function checks its rules from the top and stops at the first one that fits. Order matters because a later rule never gets a chance once an earlier one matched. Under auto, rule 1 stops everything, so escalation and risk never matter.

    The shape of the solution

    The design splits the work in two so the rule lives in one place. Plain functions in hooks/routing.js read the three inputs and answer "which family for this call". The skills then pass that answer as model. Later, the gate in E3 can run the same function over the real calls it sees and compare. Nothing in routing.js touches files, the clock or the network, so tests can call it with plain values.

    • agents/boxbox-builder.mdnew

      Its one job: build one task test-first from its brief, commit, and return a diff summary and the test result.

    • agents/boxbox-scout.mdnew

      Its one job: look things up in the repo and report. It never edits.

    • agents/boxbox-runner.mdnew

      Its one job: run checks and make mechanical fixes only, never change behaviour or logic.

    • agents/boxbox-writer.mdnew

      Its one job: fill templates from facts it is given and run the checker; where a fact is missing it writes unknown.

    • hooks/routing.jsnew

      Its one job: pure, zero-dependency functions that parse the config, the plan and the events and compute the expected model. Used by tests now and by the gate in E3.

    • hooks/boxbox-event.jschanged

      What changes: parseConfig also returns models, parallel and modelsWarning, by calling routing.parseModels, which is the one owner of the missing and unknown value rule. SAY_FORM (hooks/boxbox-event.js:262) also pre-approves say escalated.

    • skills/boxbox-setup/kit/pitwall/saychanged

      What changes: a new verb, escalated.

    • Skillschanged

      What changes: setup asks for models:; plan tags size and risk and writes an epic model:; build routes and escalates; tdd, inspect, report and lessons say who runs what; the kit GUIDE.md documents the config block, the task line and the escalated event.

    Each agent's body is a short strict prompt with a "Never" list. Builder never touches files outside its brief or anything in .boxbox/. Scout never edits. Runner never changes behaviour or logic. Writer never invents facts and labels what it does not know as unknown. Tools are the minimum each job needs.

    Interfaces

    An agent file starts with a block of settings. The model line is a fallback only: Boxbox passes model on every call (decision D1 in the plan).

    The rules for expectedModel are checked from the top, and the first one that matches decides. Under auto the function returns no model and the skill leaves model out of the call. Discover, decisions, plan, design, briefs, inspect, fact-check and approvals are never handed to these agents.

    models:
    Which cost mode the repo uses. best keeps everything on the session model, balanced is the recommended middle, save uses the smallest model that does the job, and auto passes no model at all. A missing line means auto. An unknown value means balanced plus a warning.
    parallel:
    Whether tasks may run side by side. Default off; setup writes the line and mentions it, but does not ask.
    size and risk
    Tags on a task line. A missing size counts as M and a missing risk counts as no, so older plans still parse.
    model on an epic
    Optional. "Use opus for E3" in chat becomes model: opus under the E3 heading, and applies to builder tasks only.
    model on the call
    A family alias or absent. Absent only under auto.

    How one request travels

    1. Setup asks which models to useskills/boxbox-setup/SKILL.md (changed)

      It recommends balanced and writes models: to config.md. It also writes parallel: off and mentions it.

    2. Plan tags every taskskills/boxbox-plan/SKILL.md (changed)

      Each task line gets a size and a risk. If you say "use opus for E3", the plan adds model: opus under E3.

    3. Build works out the model for each taskskills/boxbox-build/SKILL.md (changed)

      It reads the config, the task's tags and whether the task was escalated, computes the model with the rules above, then calls boxbox:boxbox-builder with that model and the task id at the start of the description.

    4. A builder fails, so the task is escalatedskills/boxbox-setup/kit/pitwall/say (changed)

      When the builder fails twice, or an early trigger fires, the skill runs say escalated and retries once on the session model. The early triggers are a diff more than three times the expected size, an edit to a file outside the task's files, and five edits to one file without the test going green. Until briefs exist in E2, expected size comes from the size tag: S 50, M 150, L 400 changed lines. If the retry fails too, the skill stops and asks you. E1 applies these rules in the build skill; E3 enforces them in the gate.

    5. Scout and runner calls work the same wayhooks/routing.js (new)

      They get their model from the same function. Page filling for reports goes to the writer. If something fails after the agent returns, it comes back as a normal result for the skill to handle.

    Risks, and what this locks in

    • highAgent names are public

      Skills, the gate in E3 and every later epic call boxbox:boxbox-builder and its siblings by name. Renaming one means editing every skill and every test that mentions it, and any page that already quotes it.

    • highMode names and task-line tags are written into user files

      best, balanced, save, auto live in each repo's config.md, and size: and risk: live in every plan.md that plan writes. Renaming them leaves old repos with values the parser reads as unknown.

    • mediumThe escalated event kind and the task id prefix

      The pit wall and the gate will read events by kind. The E3 gate and the E4 cost attribution match calls to tasks by the task id placed first in the call description. Changing either later breaks that match without any error.

    • mediumMissing models: line means auto

      0.6 repos keep 0.6 behaviour until setup asks. The cost is that they save nothing until someone runs setup again.

    • lowWidening the say pre-approval

      Today the allow-list at hooks/boxbox-event.js:262 accepts only stage and ask. E1 adds escalated to it, so the retry does not stop on a permission prompt. It is one more verb on a pattern that still allows no shell operators.

    • mediumAn environment override can defeat routing

      With CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1 set, every agent runs on that model regardless of the call (docs/routing-spike.md, section 3). Detecting that belongs to the later gate, not to E1.
