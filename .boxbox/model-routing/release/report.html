    What now exists, and how to see it working

    Some words first, because this stack is new to you. A subagent is a second Claude run that the main agent starts with the Agent tool. It gets a fresh context, its own tool list and its own model, and it returns one message. Model routing means choosing that model per call: a cheap one (Haiku, Sonnet) for routine work, the session's own model (here Opus) for work that needs judgement. The background is on the page Subagents and model routing in Claude Code.

    What a person can do now that they could not in 0.6: set models: balanced in .boxbox/config.md and have Boxbox build tasks through boxbox:boxbox-builder (Sonnet), search through boxbox:boxbox-scout (Haiku), run checks through boxbox:boxbox-runner (Haiku) and fill pages through boxbox:boxbox-writer (Sonnet). Every task gets a written brief. A hook checks each call against the rule and denies a wrong one. The pit wall shows tokens, cost and cache-read share per model, a status line shows the current task under the prompt, and parallel: on builds independent tasks together in git worktrees. Under models: auto, which is what every 0.6 repo has, none of it changes: no Boxbox agent is called.

    The request path

    Follow one builder call. A hook is a script Claude Code runs when something happens (a session starts, a tool is about to run). The one that matters here fires on PreToolUse, before a tool call, and may print JSON that denies the call. Boxbox's hooks are bash scripts that hand the work to Node.js. The steps below are in the order the call meets the code, not the order it was written.

    1. The repo says how much to spend: models: in config.mdhooks/routing.js:17

      parseModels reads models: and parallel:. A missing line means auto, which keeps 0.6 behaviour. A value it does not know runs as balanced and raises a warning that the session start shows to you and to the agent.

    2. The plan tags each task with a size and a riskhooks/routing.js:33

      parsePlanTasks reads | size: S|M|L | risk: yes|no from each task line of plan.md and an optional model: line per epic. A missing size is M, a missing risk is no.

    3. The build skill writes the task's brief, just before building itskills/boxbox-build/SKILL.md:34

      A brief is a short file, tasks/<task id>.md, with the goal, the files, the interface, the tests and the commands. It exists so a fresh builder with no memory of the chat has everything. Writing it is judgement, so the session model does it.

    4. The main agent calls the Agent tool with the right modelskills/boxbox-build/SKILL.md:36

      The call names subagent_type: boxbox:boxbox-builder, starts its description with the task id (E2.3 ...) and passes model as a family alias. Under auto it passes none and uses a plain subagent.

    5. The bash hook decides whether this call must wait for the checkhooks/boxbox-event:52

      Most hook events are logged in the background so the agent never waits. Three kinds wait for node: SessionStart, pit wall commands (for pre-approval), and, new in 0.7, an Agent or Task call from Claude Code. A call carrying turn_id is Codex, and Codex never takes this path.

    6. runGate collects what the rule needshooks/boxbox-event.js:404

      It reads state.md, the feature's plan.md, the environment (is CLAUDE_CODE_SUBAGENT_MODEL_FORCE set), the escalation history from events.jsonl, the settings files for worktree calls, and the session's model. If anything throws, it logs gate-error and lets the call through (decision D4).

    7. gateDecision compares the call with expectedModelhooks/routing.js:187

      It finds the agent and the task, stands aside under auto or FORCE, denies a call with no task id or an unknown one, applies the escalation history, then asks expectedModel (line 134) and checks that the family of the passed model equals the answer.

    8. The hook denies or allowshooks/boxbox-event.js:426

      Every decision is logged as a gate event. Only a denial prints anything: JSON with permissionDecision: "deny" and a reason that names the agent and the model to use. The main agent reads the reason and calls again. An allowed call prints nothing.

    9. SubagentStart registers the subagent's transcript and ties it to its taskhooks/boxbox-event.js:547

      A transcript is the JSONL file Claude Code writes for a run, and every message in it carries its token usage and model. The hook derives the subagent's transcript path (Claude Code gives none at start) and registers it in sessions.jsonl, so tokens count while the subagent runs. subagentTask (line 331) reads the subagent's meta.json, whose toolUseId names the Agent call, and finds the task in the gate event for that call.

    10. The server counts tokens by modelskills/boxbox-setup/kit/pitwall/server.js:316

      It reads every registered transcript, keeps one entry per message id, prices each entry at its own model's rate, and groups by model, by epic and by task. It also computes the saved-versus-session-model estimate (line 178). For background on why cache reads are priced separately, see Prompt caching and token accounting.

    11. The pit wall and the status line show itskills/boxbox-setup/kit/pitwall/statusline:29

      The pit wall page draws model chips, a lane per agent, Timing by model and a Home readout from the server's state. The status line is a separate small Node script that Claude Code runs itself; it reads the tail of .boxbox/live/events.jsonl and prints one line with the task, the agent and its model, the session cost and the test count.

    The agent file: a fixed model and minimal tools

    A plugin subagent is a Markdown file whose frontmatter names its model and tools; the body is its system prompt. A call's model beats the file's model: (spike section 2), so the file's model is only the fallback when Boxbox passes none. Boxbox always passes one, and the gate checks it (decision D1).

    The rule: first match wins

    expectedModel is a plain function over a mode and a task's tags, so it can be table-tested without Claude Code. Rule order matters: an escalation beats an epic override, which beats risk, which beats the mode table.

    The gate's last step: escalation, then equality

    Escalation means retrying a task once on the session model after a cheap builder failed it twice. The history comes from finished builder runs in events.jsonl, in file order, because the event writer stamps whole seconds and cannot order two events in the same second.

    The bash hook's synchronous path

    The deny output

    Claude Code reads the hook's standard output as JSON. A permissionDecision of deny stops the call and hands the reason text back to the model, which is how the builder retried on Opus in the live check.

    Tying a subagent to its task

    Counting tokens by model

    Prompt caching lets Claude reuse an unchanged prompt prefix at a lower price. Each transcript line reports fresh input, cache writes, cache reads and output, and each has its own rate. So cost is computed per entry at that entry's model, and the cache-read share of a model is cache reads over all input it sent.

    The status line

    Claude Code can run a command after every update and show its first line under the prompt. A plugin cannot provide that setting (spike section 9), so setup asks before writing it into the project's settings. The command gets the session as JSON on stdin.

    Worktrees. A git worktree is a second checkout of the same repository on its own branch, so two builders can edit at once without touching each other's files. Boxbox uses them for parallel: on: each builder commits on its own branch, and the main agent cherry-picks the commits in plan order onto a temporary <epic>-batch branch, runs the full suite once, and fast-forwards. See Git worktrees and merging parallel work. This path was tested with real git in a scratch repo but never run live with two Boxbox builders.

    Decisions made while building

    D1 to D5 and A1 to A22 are in .boxbox/decisions.md and on the decisions page. These are the ones where the build departed from your spec or found something the spec did not know.

    • D2: a writer subagent over model: lines in skills. A skill's model lasts the whole turn and is fixed per plugin, so it cannot follow models: (spike section 4). The cost is one more agent file to maintain.
    • D3: parallel needs worktree.baseRef: "head" over trusting Claude Code's default. The default branches a worktree from the remote's default branch, so the epic's commits were missing (spike section 7). The cost is a setup question and a refusal when the setting is absent.
    • A17: models: auto means no Boxbox agents over "agents with no model passed". With no model passed, the agent file's model wins (spike section 2), which is not "Claude Code decides". The cost is that auto repos build exactly as in 0.6.
    • The status line labels its cost "session" over showing a per-unit figure. Claude Code's number covers the whole session, main agent and subagents; the exact per-unit, per-model numbers are on the pit wall. The line differs from your spec example by that one word.
    • The 3x diff check stays in the build skill over the gate. The gate sees an Agent call, not a diff, so it cannot measure one.
    • The gate fails open in a session's first turn over guessing the session model from settings or environment. Found live: PreToolUse fires before Claude Code has written the transcript, so the session model is not on disk yet. The Stop hook now records it for later turns. The cost is one unchecked turn per session.
    • Escalation history resets on review, approval or a new plan, not on a resume, so a task paused and resumed is never escalated twice, and rework after your review starts fresh.
    • Sonnet 5.5 cache reads priced at $0.10 per million; prices.json had twice that. Claude Code's own cost for a real subagent matched only at the lower rate.

    Check yourself

    1. Why does the gate compare the call's model with a computed answer instead of trusting the agent file's model?
      A call's model beats the agent file's, so a main agent that passes the wrong model overrides the file. The gate computes the expected family from the mode, the task's tags and its history (hooks/routing.js:187), and denies a mismatch. The file's model is only the fallback.
    2. What happens if plan.md cannot be parsed, or the session model is not on disk yet?
      The gate allows the call and logs it: an exception becomes a gate-error event (hooks/boxbox-event.js:419), and an unknown session model gives "session model unknown, not checked" (hooks/routing.js:221). It fails open because a wrongly blocked session is worse than one unchecked call.
    3. Why is the escalation history built from the order of lines in the log and not from timestamps?
      The say command stamps whole seconds, so two events in the same second cannot be ordered by time. File order is the true order (comment above builderHistory, hooks/routing.js:156).
    4. Why can the pit wall count a subagent's tokens before it finishes, and how does it know which task they belong to?
      At SubagentStart the hook derives the transcript path from the parent's path and the agent id and registers it (hooks/boxbox-event.js:556). The task comes from the subagent's meta.json toolUseId, matched to the gate event for that Agent call (hooks/boxbox-event.js:335).
