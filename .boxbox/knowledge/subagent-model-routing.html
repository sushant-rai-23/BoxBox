    Subagents and model routing in Claude Code

    For a developer new to Claude Code's plugin mechanics. It covers only what Boxbox 0.7 needs: what a subagent is, how Claude Code picks the model a subagent runs on, how a hook can stop a subagent call and say why, what a status line is, and why any of this saves money. Afterwards you can read the 0.7 plan's routing epics and judge whether each step is real or wishful.

    The idea in plain words

    Where you'll meet it

    • hooks/hooks.json
    • hooks/boxbox-event.js
    • skills/boxbox-build/SKILL.md
    • docs/routing-spike.md

    Claude Code is a program that runs Claude in your terminal. The Claude you talk to is the main agentThe Claude session you type into. It reads files, runs commands and can start subagents.. It can hand a job to a subagentA second Claude started by the main agent, with its own empty context, its own instructions and its own tool list.: a fresh Claude that starts with an empty memory of the conversation, does the job, and sends back only its final answer. The docs say each subagent "runs in its own context window with a custom system prompt, specific tool access, and independent permissions" (Subagents docs). A context windowEverything the model can see in one request: instructions, the conversation so far and file contents. It is paid for in tokens. is everything the model sees at once.

    Each subagent can run on a different model: Opus (the largest and most expensive), Sonnet (middle) or Haiku (small and cheap). Model routing means choosing, for each job, which model does it (Model configuration docs).

    Analogy: a head chef (the main agent) sends prep work to kitchen staff. Each cook gets a written ticket, not the whole evening's conversation, and you pay a senior cook more than a junior one, so you send chopping to the junior. The analogy stops being true in one place: a cook remembers yesterday, a subagent remembers nothing except the ticket it was handed.

    Why it exists

    Two problems, and both cost money. First, price per tokenA chunk of text, roughly three quarters of a word. Models are billed per million tokens read (input) and written (output). differs a lot by model. The price table Boxbox ships, skills/boxbox-setup/kit/pitwall/prices.json, lists these US dollar prices per million tokens:

    ModelInputOutputCache readCompared with Opus
    claude-opus-5-5$4$20$0.201x
    claude-sonnet-5-5$2$10$0.20half the input and output price
    claude-haiku-5-5$0.10$0.50$0.01one fortieth

    Without routing, every subagent runs on the session's model. In the routing spike, the main session was Opus, and the headless test runs cost $2.70, "almost all of it Opus main-session turns" (docs/routing-spike.md). Filling a page from a template or reading files does not need the biggest model.

    Second, a long conversation fills the main agent's context window. Handing a job to a subagent keeps the work's file reads and tool output out of the main conversation; only the answer comes back (Subagents docs). That is why skills/boxbox-build/SKILL.md asks for a fresh subagent per task.

    How it works, step by step

    1. The main agent starts a subagent with the Agent tool

    Claude acts through tools: named actions such as Read, Bash or Agent, each called with a small JSON object of inputs. The Agent tool starts a subagent. "In version 2.1.63, the Task tool was renamed to Agent", and Task still works as an alias (Subagents docs). Its inputs are a description, the prompt (the ticket), the subagent_type (which agent definition to use) and, optionally, a model.

    2. Agent files describe each kind of subagent

    A plugin (a folder that adds skills, hooks and agents to Claude Code) ships agents as Markdown files in agents/<name>.md. The top of the file, between two --- lines, is frontmatter: settings written as key: value. Only name and description are required; tools limits which tools it may use, model picks its model, and isolation: worktree runs it in a separate copy of the repo. The text below the frontmatter is the subagent's instructions (Subagents docs, Plugins reference).

    This is the real test agent from the spike. A plugin's agent is named <plugin>:<name>, so this one was called as spike:spike-sonnet. Plugin agents ignore hooks, mcpServers and permissionMode.

    The description is what the main agent reads when choosing an agent; only model: sonnet decides the model. This repo has no agents/ folder yet, so Boxbox 0.7 would add the first agent files.

    3. Claude Code resolves the model

    The first rule that applies wins, checked in this order: (1) CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1 together with CLAUDE_CODE_SUBAGENT_MODEL set: that model, always; (2) the Agent call's model input; (3) the agent file's model: (inherit means the session's model); (4) CLAUDE_CODE_SUBAGENT_MODEL on its own, as a default; (5) the main session's model. An environment variable is a named setting the shell passes to every program it starts. The spike confirmed each step: a plain CLAUDE_CODE_SUBAGENT_MODEL=haiku did not change spike-sonnet; adding FORCE did (docs/routing-spike.md).

    The docs list the same order for steps 2 to 5, note that before v2.1.251 the variable came first, and that forcing one model on every subagent needs CLAUDE_CODE_SUBAGENT_MODEL_FORCE set to 1 (Subagents docs).

    A skill (a Markdown instruction file Claude loads on demand) can also carry model: in its frontmatter. That switch is short-lived: "The override applies for the rest of the current turn ... The session model resumes when you send your next prompt" (Skills docs). The spike saw exactly that: the skill answered on Sonnet, the next prompt on Opus. There is also a model setting called opusplan that uses Opus in Claude Code's plan mode and Sonnet otherwise (Model configuration docs); Boxbox 0.7 does not use it, because it follows Claude Code's plan mode, not Boxbox's plan stage.

    4. Hooks watch, and can say no

    A hook is a command Claude Code runs when an event happens, such as "a tool is about to run" (PreToolUse), "a subagent started" (SubagentStart) or "a subagent finished" (SubagentStop). The command receives the event as JSON on stdin (standard input: the text piped into a program). A PreToolUse hook can block the call by printing JSON with hookSpecificOutput.permissionDecision set to "deny" and a permissionDecisionReason; Claude Code "blocks the tool call, and shows Claude the reason". Exiting with code 2 also blocks, with stderr as the reason (Hooks docs).

    Reading the diagram top to bottom: the main agent asked for spike:spike-haiku. The spike's PreToolUse hook printed the deny JSON. The main agent read the reason, retried with spike:spike-sonnet, the hook printed nothing (so the call was allowed), and the subagent ran on claude-sonnet-5-5. When it ended, SubagentStop fired with the subagent's transcript path (docs/routing-spike.md).

    What the two subagent hooks receive differs. SubagentStart gets session_id, transcript_path (the parent's), cwd, prompt_id, agent_id, agent_type and hook_event_name, with no model and no subagent transcript. SubagentStop adds agent_transcript_path, last_assistant_message, stop_hook_active and permission_mode. The model a subagent really used is read from its own transcript file (docs/routing-spike.md).

    5. A status line shows the result

    A status line is a command named under statusLine in a settings.json file. Claude Code pipes session JSON (model, cost, context use) to it on stdin and shows the one line it prints under the prompt (Status line docs). A plugin cannot ship one: from a plugin's settings.json, "Only two keys take effect from a plugin, agent and subagentStatusLine" (Plugins reference). So Boxbox setup has to offer to write it into the project's .claude/settings.json.

    How this repo uses it

    Today Boxbox watches subagents but does not route them: no agent file in this repo names a model, and no hook denies a call to pick another model. The pieces already in place are these.

    • hooks/hooks.json:35: registers a PreToolUse hook with matcher * (every tool), running hooks/boxbox-event. Today it only pauses or logs; 0.7's routing gate would live here.
    • hooks/hooks.json:105 and hooks/hooks.json:116: register SubagentStart and SubagentStop with the same script.
    • hooks/boxbox-event:50: the bash wrapper runs Node synchronously (Claude Code waits for it) only for SessionStart and for pit wall commands; every other event, including the subagent ones, is logged in the background so the agent never waits. A deny decision must be printed synchronously, so a routing gate has to be added to this line's condition.
    • hooks/boxbox-event.js:105: classify treats a call to Agent, Task or Codex's spawn_agent as kind crew. Matching both Agent and Task matters: the spike saw hooks get Agent while the session result named the denied call Task.
    • hooks/boxbox-event.js:200: laneFor puts an event in the driver lane when there is no agent_id, the steward lane for reviewer-like agent types, and the crew lane otherwise.
    • hooks/boxbox-event.js:406: the SubagentStart and SubagentStop case logs a crew event and, on stop, records the subagent's transcript so the pit wall can count its tokens.
    • skills/boxbox-build/SKILL.md:34: "Fresh context if you can": each build task goes to a new subagent with only the task's ticket.
    • skills/boxbox-inspect/SKILL.md:21: suggests a different model for the reviewer than the one that built the unit.

    If the SubagentStart/SubagentStop registrations were removed, the pit wall would still see the Agent call through PreToolUse, but would lose the crew lane's start and finish marks and the subagent transcripts it counts tokens from.

    2. Call 1: no model passed, agent file says sonnetagent-a4bdf961…

    3. Call 2: same agent, call passes model haikuagent-aba355d9…

      Rule 2 beats rule 3: it ran on claude-haiku-5-5. Only this subagent's meta has "model":"haiku", so the meta file records what the call asked for.

    4. Call 3: agent file says haikuagent-af6a4b96…

      Rule 3 again, on Haiku. The PreToolUse lines show the hook saw the tool as Agent, and saw model only when the caller passed one. When it is absent, a gate has to work out the model itself from the agent file.

    5. Joining a subagent to its callmeta toolUseId

      Each meta's toolUseId is the id of the PreToolUse event for that Agent call. That is how the pit wall can say "this call, gated here, ran on this model".

    Two Agent calls reached the hook, but only one subagent transcript exists: the denied spike-haiku call never started a subagent. The main agent's reply quotes the hook's reason word for word, which is the whole mechanism of a routing gate: the reason is the instruction.

    Common mistakes

    • trapExpecting CLAUDE_CODE_SUBAGENT_MODEL to override agent files

      Since v2.1.251 it is only a default: spike-sonnet stayed on Sonnet with the variable set to haiku. Only CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1 overrides everything. Check both variables before assuming a gate is in charge (docs/routing-spike.md).

    • trapPrinting a deny from a background hook

      hooks/boxbox-event:50 sends most events to Node in the background with output thrown away, so a deny printed there never reaches Claude Code and the call goes ahead. A gate must run in the foreground path.

    • trapMatching only Agent

      Hooks see tool_name: "Agent", but the session result listed the denied call under "Task". Match both names, as hooks/boxbox-event.js already does for its crew kind.

    • trapLooking for the model in the hook input

      SubagentStart has no model and no subagent transcript path; PreToolUse has model only when the caller passed one. Read the model from the subagent's transcript, or compute it with the resolution order.

    • trapTrying to ship the status line in the plugin

      It is dropped silently; only agent and subagentStatusLine take effect from a plugin (Plugins reference). Write statusLine into the project's settings instead, with the developer's consent.

    When not to use it

    Do not start a subagent for a job that needs the conversation so far, such as answering the developer's last question or a small edit to a file already open: the subagent begins with none of that context, and re-explaining it costs tokens the switch was meant to save. Do not route hard design or debugging to a smaller model just because it is cheaper; a wrong answer that has to be redone costs more than one Opus pass. For a single step inside one skill, a skill's model: is the wrong tool too, because it switches the whole turn, not part of it (Skills docs); a small separate agent fits better.

    Check yourself

    1. An agent file says model: sonnet, the call passes model: "haiku", and CLAUDE_CODE_SUBAGENT_MODEL=opus is set without FORCE. Which model runs?
      Haiku. The call's model (rule 2) beats the agent file (rule 3), and the variable without FORCE is only a default (rule 4). Run a's second subagent shows rules 2 and 3.
    2. What happens if the routing gate's deny is printed from the background branch of hooks/boxbox-event:50?
      Nothing stops the call. Claude Code reads the hook's stdout, but the background branch sends Node's output to /dev/null and the wrapper exits 0 at once, so the call is allowed.
    3. Why can't the gate just read the model from SubagentStart?
      That event has no model field, and it fires after the call was already allowed. The decision belongs in PreToolUse, which runs before the subagent exists.
    4. A skill sets model: sonnet. What model answers the developer's next message?
      The session's model again. A skill's model lasts for the rest of the current turn only; the spike saw Sonnet for the skill, then Opus on the next prompt.
    5. Why does Boxbox setup have to write the status line into .claude/settings.json instead of the plugin?
      From a plugin's settings, only agent and subagentStatusLine take effect; statusLine is dropped.
