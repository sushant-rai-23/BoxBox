    Git worktrees and merging parallel work

    For a developer new to git worktrees and merges. It covers only what Boxbox 0.7's optional parallel mode needs: several builder agents each working in their own folder on their own task branch, and their commits brought back into the epic branch one at a time. Afterwards you can read a parallel-mode plan, spot a worktree that started from the wrong branch, and decide what to do when two tasks collide.

    The idea in plain words

    Where you'll meet it

    • skills/boxbox-setup/kit/GUIDE.md, "Git model"
    • skills/boxbox-build/SKILL.md, "Branches"
    • .claude/worktrees/ when parallel mode runs

    First, the basics. A commitA saved snapshot of every tracked file, with a message, an author, a date and a pointer to the commit before it (its parent). Its id is a hash such as 743704d. is a saved snapshot of the project that points back at the commit before it, so the commits form a chain called the history. A branchA movable name that points at one commit. Committing on a branch moves the name forward to the new commit. is just a name that points at one commit; when you commit on it, the name moves forward. The folder where you edit files is the working treeThe ordinary folder of files you edit. git compares it with the last commit to see what changed., and the hidden .git folder holds every commit and branch.

    Normally one repository has one working tree, so you can have only one branch checked out at a time. A worktreeAn extra working folder linked to the same .git, checked out on its own branch. is a second (or third) working folder, checked out on a different branch, that shares the same .git. A commit made in any of the folders lands in the one shared history, so every folder can see every other folder's branches.

    The analogy: one shared kitchen pantry (the .git) with several cooking stations (the folders). Each cook works on their own dish at their own station without bumping elbows, and anything they finish goes back into the same pantry. Where it stops being true: two cooks can still write different versions of the same recipe card, and nobody notices until someone tries to put both cards in one binder. That is a merge conflict, covered below.

    MergingCombining the changes from one branch into another branch. is bringing the commits from a task branch back onto the epic branch. Boxbox would do that one task at a time, in plan order.

    Why it exists

    Without worktrees, a repository has one folder and one checked-out branch. Two agents editing at the same time in that folder would edit the same files on the same branch: one agent's half-written change breaks the other's test run, and their commits mix. git's answer is to let one repository support several working trees, "allowing you to check out more than one branch at a time", each linked worktree "sharing everything except per-worktree files such as HEAD, index" (git-worktree documentation).

    Claude Code uses this for parallel agents: running each session in its own worktree "gives it a separate copy of the files to edit, so one session can build a feature while a second fixes a bug", and subagents "can run in their own worktrees so parallel edits don't conflict" (Claude Code: Run parallel sessions with worktrees).

    A separate folder isolates the edits, not the outcome. Two tasks can still change the same line, and that only shows up when the second one is merged. git then stops and marks the conflicting lines with <<<<<<<, ======= and >>>>>>> for a person to resolve (git-merge documentation, "How conflicts are presented"). This is why parallel mode needs a plan for merging, not only for running.

    How it works, step by step

    Step 1, create a worktree. git worktree add -b task-1 ../wt-task-1 epic makes a new folder ../wt-task-1, creates a new branch task-1 starting at the commit epic points to, and checks it out there. The doc: "Create a worktree at <path> and checkout <commit-ish> into it" (git worktree add). git refuses to check out a branch that is already checked out in another worktree, unless forced, so two folders can never share one branch.

    Step 2, see them. git worktree list lists the main worktree first, then each linked one, with the commit and branch each has checked out (git worktree list).

    Step 3, work in each folder. Each folder is ordinary: edit, test, commit. I ran this in a scratch repository (never in this repo) with fixed names and dates so the hashes repeat. Paths are shortened to wt-demo/; the full scratch path is longer.

    The graph shows two commits side by side, both with parent adeea03. Neither task knows about the other. epic has not moved yet: it is still at adeea03.

    Step 4, bring them back, one at a time. There are three ways to put a task's commit onto epic. A fast-forward happens when epic is still at the task's starting point: git just moves the epic name forward to the task's commit, "without creating an extra merge commit"; --ff-only refuses if that is not possible (git merge). A merge commit (git merge --no-ff) adds a new commit with two parents that joins the histories. A squash (git merge --squash) stages the combined change but makes no merge commit, so you write one ordinary commit yourself (git merge --squash). A cherry-pick takes an existing commit, applies the change it introduced, and records a new commit for it on the current branch (git cherry-pick).

    Task 1 fast-forwarded: epic now points at the very commit made in the worktree, 743704d. Task 2 could not fast-forward, because epic had moved past task 2's starting point. The cherry-pick copied its change on top as a new commit, e3d8d8a, with a new hash; the original 6f125a2 still hangs off adeea03 on task-2. The result is a straight line on epic, one commit per task, in plan order.

    Step 5, a conflict. When two tasks change the same line, git cannot choose. The cherry-pick stops, leaves the branch "at the last commit successfully made", and writes both versions into the file between conflict markers; git cherry-pick --abort returns to the state before it started (git cherry-pick, conflicts and --abort).

    UU means the file is unmerged on both sides. The part above ======= is what epic already has (task 3); below is task 4's change. After the abort, epic is back at a6c33ad with task 3 only, untouched.

    Step 6, clean up. git worktree remove <path> deletes a linked folder; it refuses an unclean one (untracked or modified files) unless you add --force, and the main worktree cannot be removed (git worktree remove). Removing the folder does not delete its branch: that is a separate git branch -d.

    The two removes print nothing on success. task-1 deletes cleanly because its commit is on epic. task-2 is "not fully merged" because its original commit 6f125a2 is not on epic; only the cherry-picked copy is. Check the change is really on epic before forcing with -D.

    How this repo uses it

    No worktree code yet. At commit 3825189, git grep -i worktree finds nothing in any tracked file. Parallel mode is a plan for 0.7. What exists today is the branch model it must fit into.

    • skills/boxbox-setup/kit/GUIDE.md:282: each feature gets a feature branch off the main branch. (The installed copy is .boxbox/GUIDE.md, same lines.)
    • skills/boxbox-setup/kit/GUIDE.md:283: with unit = epic, each epic gets its own branch off the feature branch, one commit per task, and the epic is squash-merged into the feature branch on approval.
    • skills/boxbox-build/SKILL.md:24: the build skill creates the epic branch from the feature branch.
    • skills/boxbox-build/SKILL.md:37: one commit per task, code and tests only, never with a failing check.

    So parallel mode adds one layer below the epic branch: a short-lived task branch per builder, each in its own worktree, whose single commit comes back onto the epic branch. After that the epic branch must look exactly as it does in sequential mode, one commit per task in plan order, so the review stop and the squash-merge (line 283) do not change. That is why a cherry-pick or a fast-forward fits and a merge commit does not: a merge commit would add an extra commit per task to the epic branch.

    The 0.7 routing spike (docs/routing-spike.md, section 7, not yet committed) ran a real isolation: worktree subagent. It ran in <repo>/.claude/worktrees/agent-<agent_id> on a new branch worktree-agent-<agent_id>, its commit stayed on that branch, and the Agent tool result returned agentId, worktreePath and worktreeBranch. The .claude/ folder showed up untracked in the main checkout.

    The gotcha that matters most: with a remote whose default branch was master and the session on epic, the worktree branched from master and the epic's commits were missing. Without a remote it branched from the current HEAD, and with "worktree": {"baseRef": "head"} in .claude/settings.json it branched from the current branch. The spike repo's real graph shows both outcomes:

    Two agent commits (0966c85, 8f7733b) sit on top of b7c4dfd epic commit: those worktrees started from the epic. Two (42c5ab8, 0d4f943) sit directly on 9dee144 init, which is master: those started without the epic's work. The spike's conclusion is that parallel mode must set worktree.baseRef: "head" or refuse to run, and must make sure .claude/worktrees/ is ignored.

    The docs agree: subagent worktrees "branch from your repository's default branch unless worktree.baseRef is set to "head""; "head" branches "from your current local HEAD", and the setting cannot be a branch name. The docs also advise adding .claude/worktrees/ to .gitignore, and say a subagent's worktree is removed automatically when it finishes without changes, while one with changes stays on disk (Claude Code: Isolate subagents with worktrees).

    One epic with two tasks, E1.1 and E1.2, run in parallel mode as 0.7 plans it. The first two steps are today's code; the rest is the planned flow, matched to the scratch run above. Nothing after step 2 exists in this repo yet.

    1. The epic branch existsskills/boxbox-build/SKILL.md:24

      The build skill creates <feature>-e1-<slug> off the feature branch and checks it out in the main folder. In the scratch run, this is epic at adeea03. If worktree.baseRef is not "head", parallel mode must stop here.

    2. Each builder commits onceskills/boxbox-build/SKILL.md:37

      One commit per task, code and tests only, all checks green. In parallel mode each builder makes that commit in its own worktree on its own branch (worktree-agent-<id>), as the scratch run made 743704d on task-1 and 6f125a2 on task-2, both on top of adeea03. The agent result hands back worktreeBranch, which is the name the next step needs.

    3. Bring E1.1 back firstskills/boxbox-setup/kit/GUIDE.md:283

      In plan order, the first task's branch starts exactly at the epic's tip, so git merge --ff-only moves epic to 743704d. Then run the full test suite (node --test tests/pitwall/*.test.js in this repo) on the epic branch.

    4. Bring E1.2 back secondskills/boxbox-setup/kit/GUIDE.md:283

    Common mistakes

    • trapThe worktree starts from main, not the epic

      Claude Code's default base is the remote's default branch, so a builder silently works without the epic's earlier commits, and its change later lands on code it never saw (Choose the base branch). Notice it with git log --oneline --graph --all: the task commit sits on main, not on the epic. Fix: set worktree.baseRef: "head", and check the worktree's parent commit before merging.

    • trapMerging several task branches at once

      A single git merge of many branches, or merging them all before testing, hides which task broke what. Merge one task, run the full suite, then the next. A conflict stops git with conflict markers in the file (git merge); never commit a file that still contains them.

    • trapTrusting each worktree's green tests

      Each builder only tested its own change. Two changes that each pass can fail together without any textual conflict: a cherry-pick applies "the change each one introduces" as text (git cherry-pick), and git does not check meaning. Fix: run the full suite on the epic branch after every task comes back.

    • trapForgetting cleanup

      A worktree folder and its branch outlive the task. git worktree remove refuses an unclean folder without --force (git worktree remove), and a cherry-picked branch looks "not fully merged" to git branch -d. Fix: remove each folder, confirm the change is on the epic, then delete the branch. Ignore .claude/worktrees/ so the folders never show as untracked.

    When not to use it

    Do not run tasks in parallel when one task depends on another's code: a worktree is created from a fixed starting commit, so a later task cannot see an earlier task's work until it is merged (git worktree). The same goes for tasks that will edit the same lines, since the second one will conflict. For those, keep the normal sequential build: one task at a time on the epic branch, which is what Boxbox does by default. A worktree is also a fresh checkout without gitignored files such as .env (Copy gitignored files into worktrees), so a task whose tests need local setup costs more to run in one. For a one-file change, one folder and one branch is simpler.

    Check yourself

    1. Why does a worktree let two agents edit at once, when a branch alone does not?
      A branch is only a name for a commit; with one folder, only one branch can be checked out, so two agents would edit the same files. A worktree gives each branch its own folder while sharing the one .git, so their edits never touch and their commits land in the same history.
    2. What happens if parallel mode runs without worktree.baseRef: "head" in a repo with a remote?
      Each builder's worktree starts from the remote's default branch, not the epic branch, so it works without the epic's earlier commits. The spike saw exactly this: two agent commits sit on 9dee144 init instead of on b7c4dfd epic commit. Boxbox should refuse to run parallel mode in that state.
    3. In the scratch run, why did task 1 fast-forward but task 2 need a cherry-pick?
      Both started at adeea03. After task 1 fast-forwarded, epic was at 743704d, no longer task 2's parent, so --ff-only refused. A cherry-pick re-applied task 2's change on top as a new commit, e3d8d8a.
    4. Why does Boxbox prefer cherry-pick or fast-forward over a merge commit for task branches?
      The git model wants one commit per task on the epic branch (skills/boxbox-setup/kit/GUIDE.md:283). Fast-forward and cherry-pick each add exactly the task's commit; a merge commit adds an extra joining commit per task. The squash belongs one level up, epic into feature, on approval.
    5. A cherry-pick stops with CONFLICT. What state is the epic branch in, and what should Boxbox do?
      The branch stays at the last commit that succeeded and the file holds conflict markers. Boxbox runs git cherry-pick --abort to get back to that clean state, then builds that task again sequentially on the updated epic branch, instead of guessing a resolution.
