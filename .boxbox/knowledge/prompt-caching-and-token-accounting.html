    Prompt caching and token accounting

    For a developer new to Claude's billing. It covers what a token is, what prompt caching does to the price of a call, why the order of a prompt matters, and how the pit wall turns Claude Code's transcript files into tokens and dollars per model. Afterwards you can read the token code in skills/boxbox-setup/kit/pitwall/server.js, check a cost by hand, and see why Boxbox 0.7 sends each subagent "the fixed part, then the brief".

    The idea in plain words

    Where you'll meet it

    • skills/boxbox-setup/kit/pitwall/server.js
    • skills/boxbox-setup/kit/pitwall/prices.json
    • Claude Code transcripts in ~/.claude/projects/

    A model does not read characters. It reads tokensThe small pieces text is cut into before the model reads it: a word, part of a word, or a character.: small pieces of text, each a word, part of a word, or a single character. For recent Claude models one token is a few English characters (Anthropic glossary, "Tokens"). Everything is billed per token: the tokens you send in (the input: instructions, files, the conversation so far) and the tokens the model writes back (the output), at different prices per million tokens (pricing).

    Prompt caching means the API remembers the start of a prompt it has just seen. If your next call begins with exactly the same text, the API reuses its work on that start instead of reading it again, and charges you far less for it. Storing the start is a cache write; reusing it is a cache read (prompt caching docs).

    An analogy: a photocopy shop that keeps your cover pages on the glass for a few minutes. If your next job starts with the same cover pages, they only charge you for the new pages and a small fee for the cover. Change one letter on the first cover page, or come back too late, and you pay full price for everything again. Where it stops being true: the shop charges extra the first time it keeps your pages, and it only matches from the very first page onward, never a page in the middle.

    Token accounting is the other half: adding up, per model, how many tokens of each kind were used and what they cost. Boxbox's pit wall does this by reading the transcript files Claude Code writes, not by asking the API.

    Why it exists

    An agent like Claude Code sends the whole conversation again on every call: the tool definitions, the system instructions, every earlier message, then the new part. Without caching, a long session pays the full input price for the same opening text on every single turn. With caching, the repeated part is charged at a cache-read price, which the docs set at 0.1 times the base input price, and 0.05 times on Claude Opus 5.5 and Claude Sonnet 5.5 (pricing).

    A concrete case from this repo's routing spike: the main Opus session in the worked example below sent 188,555 input tokens over four calls, and 161,881 of them (85.9%) were cache reads. Run through the pit wall's own cost function, those four calls cost $0.254876. Charging every input token at the normal Opus input price instead gives $0.763360, three times as much.

    Token accounting exists because Boxbox 0.7 routes work to cheaper models (Sonnet, Haiku) and needs to show what that saved. The pit wall's cost code (skills/boxbox-setup/kit/pitwall/server.js:133) prices each kind of token separately, because a cache read and a fresh input token of the same model differ in price by a factor of 20.

    How it works, step by step

    1. The prompt has a fixed order. The API treats a request as tools, then system, then messages, in that order, and caching covers the prompt from the very start up to a marked point (prompt caching).
    2. First call: cache write. The start of the prompt is not cached yet, so the API reads it in full and stores it. Those tokens are billed as cache writes: 1.25 times the base input price for the default 5-minute lifetime, 2 times for a 1-hour lifetime (prompt caching).
    3. Next call, same start: cache read. A hit needs the cached part to be 100% identical, every character. The matched tokens are billed as cache reads, and each read refreshes the lifetime at no extra cost (prompt caching).
    4. The rest is plain input. Whatever comes after the cached part (the new brief, the newest message) is ordinary input at the base price, and the model's reply is output (prompt caching, usage fields).
    5. A change early breaks everything after it. Changing tool definitions invalidates the whole cache; changing the system part invalidates the system and messages; and the docs warn that timestamps or per-request text inside the cached part mean the prefix "never matches" (prompt caching). So the rule is: fixed part first, changing part last, no timestamps in the fixed part. That is why Boxbox 0.7 will give each subagent the same fixed part followed by its brief.
    6. Too short is never cached. Below a minimum length (512 tokens for Opus 5.5, Sonnet 5.5 and Haiku 5.5) the prompt is simply not cached, with no error (prompt caching, minimum length).

    The API reports the split in each response's usage: cache_creation_input_tokens (written), cache_read_input_tokens (read) and input_tokens (only what came after the last cache point), so all the input of a call is the sum of the three (prompt caching, usage fields). The cost is each count times its price per million tokens, divided by one million. The rates for this repo's models, from the pricing page, in dollars per million tokens:

    ModelInput5m write1h writeCache readOutput
    Claude Opus 5.54580.2020 (pricing)
    Claude Sonnet 5.522.5040.1010 (pricing)
    Claude Haiku 5.5, prompts up to 100,000 tokens0.100.1250.200.010.50 (pricing)

    The cache-read share is how much of all input came from the cache: cache reads divided by (input + cache writes + cache reads). It is the one number that tells you whether prompt order is working. The pit wall's add keeps the same split, fresh and cache, at skills/boxbox-setup/kit/pitwall/server.js:147.

    How this repo uses it

    Boxbox never calls the API to learn token counts. The pit wall follows the transcript files Claude Code and Codex already write, one JSON object per line (the format called JSON Lines), and turns each assistant message into one entry with five counts: input, output, cacheWrite5m, cacheWrite1h and cacheRead. If these functions were removed, the pit wall's token and cost numbers, and the cost on every report page, would disappear.

    • skills/boxbox-setup/kit/pitwall/server.js:75: usageTotal adds the five counts. It is only used to compare two lines of the same message.
    • skills/boxbox-setup/kit/pitwall/server.js:79: ingestClaudeLines reads Claude Code lines. It keeps only type: "assistant" lines with message.usage (line 85), reads message.model and the usage fields (lines 86 to 92), prefers the 5-minute and 1-hour split under cache_creation and falls back to cache_creation_input_tokens when the split is missing (lines 90 and 91), and keeps one entry per message.id, the line with the highest total (lines 94 to 96).
    • skills/boxbox-setup/kit/pitwall/server.js:101: ingestCodexLines. Codex writes running totals for the whole session, so each turn is the new total minus the previous one (lines 111 to 118). Codex reports cached input inside its input count, so the code subtracts it (line 118). Codex has no cache-write field, so those stay 0.
    • skills/boxbox-setup/kit/pitwall/server.js:124: priceFor finds a model's rates in prices.json: the exact id, or the id plus a date suffix, longest key first so one model never takes a shorter id's price (line 127).
    • skills/boxbox-setup/kit/pitwall/server.js:133: costOf multiplies each count by its rate and divides by one million. It returns null, never a guess, when a needed rate is missing (line 139).
    • skills/boxbox-setup/kit/pitwall/server.js:146: add splits an entry into fresh (input, output, both writes) and cache (reads), and aggregate at line 198 sums entries per epic, per task and per session.
    • skills/boxbox-setup/kit/pitwall/server.js:336: readPrices loads .boxbox/pitwall/prices.json if the developer has one, otherwise the copy next to the server.
    • skills/boxbox-setup/kit/pitwall/server.js:390: refreshTokens runs each transcript the session log lists through the right reader, Claude or Codex.

    Subagents do not write into the main transcript. The routing spike found each subagent's transcript at ~/.claude/projects/<project>/<session>/subagents/agent-<agent_id>.jsonl, and the main transcript held no subagent lines, so exact per-model totals are the main transcript plus every file under subagents/, with no double counting (docs/routing-spike.md, section 5). The spike also saw that the totals Claude Code itself reports include small Haiku calls (such as the session title) that appear in no transcript, so transcript totals run slightly low on Haiku (docs/routing-spike.md, "Other observations").

    A worked example

    The routing spike session 3bb023ed ran one Opus 5.5 main session and three subagents: one on Sonnet 5.5 and two on Haiku 5.5. This script feeds its four real transcripts through the repo's own ingestClaudeLines, priceFor and costOf, with the repo's prices.json, and prints tokens, cost and cache-read share per model. It also prints what the same tokens would cost with no cache, every input token at the base input price.

      The raw cache_read_input_tokens of the four Opus calls were 21,856, then 44,320, 47,621 and 48,084.     3. Opus cost, field by fieldskills/boxbox-setup/kit/pitwall/server.js:135

      8 input × $4 = 32; 457 output × $20 = 9,140; 26,666 1-hour writes × $8 = 213,328; 161,881 reads × $0.20 = 32,376.2. The sum is 254,876.2, divided by one million: $0.254876. The writes are most of it; the reads, 86% of the input, are about an eighth of the cost.

    4. Sonnet: a write with no read costs more than no cacheskills/boxbox-setup/kit/pitwall/server.js:135

      The Sonnet subagent ran once: 4,462 tokens written at $2.50 = 11,155, plus 2 × $2 and 4 × $10, gives $0.011199. With no cache it would have been $0.008968. A cache write only pays off if something reads it.

    5. Haiku: the second subagent read what the first wroteskills/boxbox-setup/kit/pitwall/server.js:92

    Common mistakes

    • trapSomething that changes at the top of the prompt

      A date, a run id, a random order of tools or files placed before the stable text makes every call a cache miss, and every call then pays the write premium (prompt caching). You notice it as a cache-read share near zero across many calls with the same model. Fix: fixed part first, changing part last.

    • trapAdding every transcript line

      One message can be written on several lines while it streams, and summing them counts it more than once. Keep one entry per message.id, as skills/boxbox-setup/kit/pitwall/server.js:96 does.

    • trapCounting only the main transcript

      Subagent tokens live in their own files under <session>/subagents/; the main transcript has none of them (docs/routing-spike.md, section 5). Reading only the main file makes Sonnet and Haiku work invisible.

    • trapPricing a cache write as plain input, or every cache read at 0.1

      Writes cost 1.25 or 2 times input; reads cost 0.1 times on most models but 0.05 on Opus 5.5 and Sonnet 5.5 (pricing). The repo's skills/boxbox-setup/kit/pitwall/prices.json:70 has 0.2 for Sonnet 5.5 cache reads, while the pricing page lists $0.10, so Sonnet cache reads are over-counted by 2× until that line is corrected.

    • trapExpecting a short prompt to be cached

      Below 512 tokens on the 5.5 models nothing is cached and there is no error; both cache fields are just 0 (prompt caching).

    When not to use it

    Caching pays only when the same start is read again before it expires. A one-off call costs more with a cache write than without: the Sonnet subagent in the worked example paid $0.011199 against $0.008968. A Codex session gives no cache-write field at all, so its cost can only be the fresh input, the cached input and the output (skills/boxbox-setup/kit/pitwall/server.js:118).

    The docs put the break-even at one read for a 5-minute write and two reads for a 1-hour write (pricing). So the 1-hour lifetime is the wrong choice for calls that come in quick bursts, and caching at all is the wrong choice for text that changes every call. For exact billing, the transcript count is also the wrong tool: Claude Code's own small Haiku calls appear in no transcript, so use the provider's billing report.

    Check yourself

    1. Why will Boxbox 0.7 send each subagent "the fixed part, then the brief", and not the brief first?
      The cache matches from the very first token. With the fixed part first, every subagent on the same model starts identically and reads that part from the cache; the brief, which differs each time, is plain input at the end. Brief first would make each prompt differ from the start, so nothing would ever be read.
    2. What happens if someone adds "Started at 10:42:13" to the top of the shared fixed part?
      Every call's prompt now differs in its first line, so every call is a cache miss and pays the write price (1.25× input for 5 minutes) on the whole fixed part. The pit wall would show the cache-read share for that model falling to about 0%.
    3. What would happen if ingestClaudeLines summed every line instead of keeping one per message.id?
      A message streamed on several lines would be counted once per line, so tokens and cost would be too high. The byId map at skills/boxbox-setup/kit/pitwall/server.js:94 to 96 keeps only the line with the highest total.
    4. The Haiku numbers were write 4,460 and read 4,460. Compute the cache-read share and the cost of those two fields.
      Share: 4,460 / (4 + 4,460 + 4,460) = 50%. Cost: 4,460 × $0.125 + 4,460 × $0.01 = 602.1 per million, so about $0.000602; with input and output it prints $0.000607.
    5. Why is reading only the main transcript not enough for per-model totals?
      Subagents write their own files under <session>/subagents/agent-<id>.jsonl and the main transcript has none of their lines, so Sonnet and Haiku work would be missing. Main plus subagent files is exact and never double counts.
